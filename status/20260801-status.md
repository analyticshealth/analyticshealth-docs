### 0.2 Root cause do fetch-garmin

`garminconnect` library **não consegue autenticar a partir de IPs de Lambda AWS**:

- **`mobile` login** → HTTP 429 (Garmin bloqueia por IP compartilhado da AWS).
- **`widget` / `portal` login** → CAPTCHA_REQUIRED / HTTP 403 (anti-bot da Garmin).

O secret e as credenciais estão corretos (roda localmente, como comprovado pelos 6.317 objetos carregados via `initial_load` em 2026-05). O que quebrou é o mecanismo de auth do lado do provider — não é regressão do nosso código.

### 0.4 Nova direção arquitetural — Connect IQ SDK (Garmin push model)

**Decisão em 2026-08-01:** abandonar a abordagem "Lambda faz pull do Garmin Connect" e ir para "watch faz push para AnalyticsHealth" via **Connect IQ SDK** (https://developer.garmin.com/connect-iq/sdk/).

#### Por quê

- O único bloqueador da auth é o lado do Garmin (anti-bot em IPs de datacenter). Não é resolvível por upgrade de library nem por retry.
- Rodar de IP residencial (opção B/C do plano anterior) resolve tecnicamente mas sai do princípio serverless-first e cria dependência de um Mac ligado 24/7.
- Connect IQ é **oficialmente suportado pela Garmin**, gratuito, e o modelo push casa com "idle cost ≈ 0" — só há tráfego quando há dados novos.

#### Modelo alvo

```
Watch (Connect IQ data-field ou app)
   └── HTTPS POST → API Gateway /ingest (JWT device-token)
          └── Lambda receiver → S3 raw/garmin/{user_id}/{yyyy}/{mm}/{dd}/{type}.json
                └── (dispara consolidator para atualizar knowledge-base/)
```

Ao invés do EventBridge cron diário, a própria activity/sleep no relógio dispara o envio ao terminar. Delay: segundos, não 24h.

#### Trabalho a fazer (novo Passo 2b — Connect IQ path)

1. **Cadastro developer Garmin + criação de app Connect IQ** — verificar limites do SDK (data-field vs app vs widget), tipos de dados exportáveis (Activity, HRV, Sleep, Body Battery, etc.) e limites de payload / rede.
2. **Escrever ADR-0007** — Ingestion model: Connect IQ push vs Garmin Connect pull. Cobrir: tipos de dados disponíveis, autenticação (device token), lacunas (dados históricos não vêm — só a partir da instalação).
3. **Endpoint `/ingest` (Lambda + API GW)** — POST autenticado com device token; validação de schema; escrita idempotente no mesmo formato `raw/garmin/{user_id}/…` que o `initial_load` já produz. Reutilizar `manual_ingest` como base.
4. **App Connect IQ mínima** (Monkey C) — envia daily summary + sleep + HRV ao final do dia; retry com fila local se offline.
5. **Instalar no relógio pessoal do Lucas** e validar 3-5 dias de dados chegando ponta-a-ponta.
6. **Documentação** — atualizar [`docs/architecture/ingestion.md`](../docs/architecture/ingestion.md) e o [`docs/index.md`](../docs/index.md) (o diagrama Mermaid do "How it works" hoje mostra "daily sync" — passar a "watch push").
7. **Backfill histórico** — permanece via `initial_load` local (já existe, já rodou). Connect IQ cobre só o futuro.

#### O que morre com essa decisão

- ❌ `fetch_garmin` Lambda como orquestrador principal (pode ficar no repo como referência, mas fora do caminho crítico).
- ❌ Cron diário `DailyGarminSync` (já removido do CDK).
- ❌ Necessidade de armazenar credenciais Garmin em Secrets Manager (`analyticshealth/garmin-credentials` fica órfão — desprovisionar num passo futuro).
- ❌ Dependência da library `garminconnect` no Lambda layer.

#### O que sobrevive intacto

- ✅ `manual_ingest` Lambda (fluxo POST → S3, JWT Cognito) — é literalmente o esqueleto do `/ingest` novo.
- ✅ `ocr_weight` Lambda (Textract) — canal ortogonal, não afetado.
- ✅ `consolidator` (ainda a implementar) — consome do S3, indiferente à origem.
- ✅ Toda a Fase 4 (RAG + Bedrock KB) — nenhum impacto.

### Passo 1b — Estancar o sangramento (parcialmente feito em 2026-08-01)

2. ✅ DLQ purgada (§0.3).
3. ✅ CDK atualizado — falta um `cdk deploy` para propagar (§0.3).

### Passo 2 — Consolidator Lambda (2-3 dias)
Objetivo: transformar `raw/garmin/{user_id}/…` num corpus textual denso e legível por LLM em `knowledge-base/{user_id}/`.
- Definir o formato de saída (Markdown por dia? JSON estruturado com resumo textual?). **Recomendação:** um `.md` por dia com secções por tipo (`sleep`, `activities`, `metrics`, `biometrics`, `race_predictions`) — é o formato que o Bedrock KB chunker corta bem.
- Implementar `src/consolidator/handler.py`: leitura idempotente do `raw/` de N dias, merge, escrita em `knowledge-base/`. Trigger: EventBridge cron 07:00 UTC (1h após o `fetch_garmin`).
- Backfill: rodar uma vez sobre todos os 6.317 objetos existentes.
- ADR-0007 sobre o formato de consolidação (chunk-friendly, per-day, per-user).

### Passo 3 — Vector store & Knowledge Base (3-4 dias)
Ponto de decisão: [ADR-0001](../docs/decisions/adr-0001-pgvector-vs-opensearch.md) escolhe pgvector, [ADR-0005](../docs/decisions/adr-0005-rds-provisioned-vs-aurora.md) escolhe RDS provisionado. **Reavaliar** à luz de custo idle ≈ $0 — `db.t4g.micro` on 24/7 fere esse princípio. Sugestão: **Aurora Serverless v2 mínimo 0 ACU** ou **OpenSearch Serverless** (comparar TCO real).
- Implementar `AiStack`:
  - VPC + subnet privada (já existe na StorageStack? confirmar).
  - Aurora Serverless v2 pgvector, extensão `vector` criada via custom resource.
  - Bedrock Knowledge Base apontando para `s3://…/knowledge-base/` com filtragem por metadata `user_id` (defesa em profundidade multi-tenant).
  - IAM: role da KB só com acesso ao prefix e à secret do RDS.
- Executar `StartIngestionJob` e validar retrieval via `Retrieve` API.

### Passo 4 — Endpoint `/chat` + sessão (2-3 dias)
- Lambda `chat` (Python 3.12) em API Gateway `/chat` (POST, JWT Cognito).
- Fluxo: valida JWT → extrai `user_id` do claim (**nunca do body** — princípio já documentado) → `RetrieveAndGenerate` no KB com `metadata.user_id == claim.user_id` → grava turno em `analyticshealth-sessions` (TTL 90d já configurado) → retorna resposta.
